# 重构/优化程序的判定顺序：先官方 FB，后自建 FB

> 这份文档是**判定流程**，不是风格建议。它回答一个问题：
> "看到一段手写梯形图，我该不该动它、该动成什么？"
>
> 来源：2026-11 台州检测机项目复盘。原工程把基恩士官方运动 FB
> （`MC_Home/MC_Jog/MC_Reset/MC_Stop/MC_Power/MC_SyncTypeFollowUpControl`）**已经在调用**的同时，
> 又用手写梯形图把它们的内部机制（上升沿、自保持、方向互斥、忙/完成标志）重做了一遍。
> 当时的"优化"把这些手写段搬到另一个程序里、再包一层自研 FB，等于把冗余保留、只换了位置——这是反面教材。

---

## 0. 一句话规则

**先问"官方是否已经提供这个能力"，再问"这段逻辑是否值得提炼成 FB"。顺序不能颠倒。**

1. 官方 FB 能做的事 → **直接用官方 FB**，把现场信号当输入参数喂进去；
2. 官方没有该能力、且同一逻辑在多处重复 → **才提炼用户 FB**；
3. 永远不要"为官方 FB 再包一层用户 FB"，也不要把"手写重复逻辑"搬进用户 FB 就当成优化。

## 1. 识别"自建替代官方"（re-invented standard FB）

满足以下 **≥2 条**即为候选，且必须给出官方 FB 的替代方案：

| 信号 | 具体长什么样（台州实例） |
|---|---|
| 手写边沿 + 自保持 + 完成复位，围绕某个官方 FB 调用 | `LDP 面板 / ANB 手动模式 / LDP 上位 / AND 手动模式 / ORL / OR 自保持 / OR 完成脉冲 / ANB 完成 → OUT 回原触发`，再 `SET 回原完成`、`SHOT #1` |
| 官方 FB 的 `Execute/Busy/Done/Error/ErrorID` 被 `???` 掉或从不使用 | `FBEAND MC_Home MC_Home1 _MC_Axis[#1] +0 ??? ??? ??? ???`，完成后另用 `SET` 造一个"完成"位 |
| 方向互斥/互锁/忙标志手写，而官方 FB 内建 | 正/负 JOG 六条 rung：`ANB 对向 / ANB 另一路 / ANB 回原中 / ANB 同步中`，再 `LD JOG中 → OUT MRxx01`；`MC_Jog` 本来就有 `JogForward/JogBackward/Busy` |
| 同一机制在工程里出现多份手写实现 | 三个轴各一套回原/JOG/复位/停止手写状态机 |
| 命名与类别不匹配 | 模块叫 `xxx_FB`、类别却是扫描程序（`;MODULE_TYPE:0`） |

**反驳条件（自建确实有优势时才保留）**：

- 官方 FB 缺少该功能（例如平台/机型不支持、缺少某种报警保持或特殊减速曲线）；
- 自建段承载了官方 FB 无法表达的真实工艺/安全条件——注意：这类条件应作为**输入条件**喂给官方 FB，
  而不是因此放弃官方 FB；
- 官方 FB 的行为与本机设备不兼容（需给出证据，例如手册条目或实测）。

**没有证据时**：只能写成"候选（未证实）"，不得据此改工程。

## 2. 只有官方没有时，才判断"是否值得做成用户 FB"

满足全部条件才提炼：

1. **重复**：同一逻辑出现在 ≥2 处（≥2 轴 / ≥2 工位 / ≥2 程序），差异只在变量或常数；
2. **自洽**：只依赖自变量和局部状态，不直接读写全局软元件（否则调用方仍被绑死，提炼无收益）；
3. **可移植**：需要搬到别的机器，或需要独立测试/复用。

不满足时**不提炼**——"看起来像 FB"不是理由。台州案例里"回原/JOG/复位/停止"本身就不该提炼，
因为官方已经提供；真正值得提炼的是**一组官方 FB + 固定参数 + 现场差异**的整机单元（例如"轴控单元"），
且必须确有 ≥2 处复用。

## 3. 提炼成 FB 时的边界

| 放进 FB | 留在调用方（扫描程序） |
|---|---|
| 官方 FB 调用 + 它们的实例 | 现场软元件映射（按钮、指示灯、抱闸、模式开关） |
| 固定参数（速度/加减速/减速度常量） | 每个轴/工位不同的常数 |
| 由官方输出派生的状态（`Done/Busy/Error` → 对应状态位） | 跨轴动作（同步、急停）与顺序编排 |

> 判据：**FB 里出现全局软元件地址，就说明放错了**（用仓库的 `validate_fb_reuse_guard` 可以查）。

## 4. 三个反模式（本项目都踩过）

1. **给官方 FB 再包一层用户 FB**：多一个私有接口要维护，没有任何新增能力；
   ```st
   // 反面：FB_Axis 只是把 MC_Home/MC_Reset/MC_Stop 包起来
   ```
2. **把重复的手写逻辑搬进 FB**：冗余没消失，只是换了文件，还多了一层调用；
3. **为"结构好看"而改造**：把 `xxx_FB` 从扫描程序改名/搬家，但内部仍是手写状态机——名字变了，问题没变。

## 5. 未知含义的信号：不许猜、不许旁路

台州工程里有几处条件没人说得清（`R30004` 同时出现在伺服ON和 JOG 互锁里，写法是
`(X AND NOT R30004) OR R30004`，等价于"R30004 为 ON 时强行旁路"；轴3 还缺 `伺服ON` 这一路）。

处理规则：

1. **保留原条件**，作为官方 FB 的输入成员之一（例如 `JogForward := 按钮 AND 该条件`）；
2. 在报告里单列"**含义待确认的信号**"清单，写清它现在参与哪些判断、改动后的行为差异；
3. **不允许**为了让结构干净而删除、取反或旁路未知条件。

## 6. 优化交付物必须包含

| 项 | 要求 |
|---|---|
| 被删除的手写行数 | 按模块列出，并说明对应能力由哪个官方 FB 承担 |
| 保留的现场条件 | 逐条列出（设备号 + 当前注释 + 在表达式里的位置） |
| 行为差异清单 | 逐条写"改前行为 → 改后行为"；**这一项是下装前的必审项** |
| 无法替代的项 | 官方确实没有的能力，写明依据 |
| 待确认信号 | 第 5 节的清单 |

## 7. 快速自检（改之前先回答）

1. 这段逻辑的每一步，官方 FB 的哪个参数/输出对应得上？
2. 如果官方 FB 一个参数就能表达，我为什么还要保留手写？
3. 我要提炼的 FB，工程里到底有几处会调用它？
4. 改完以后，哪几处设备行为会变？我能不能逐条说清？
5. 有没有我看不懂的软元件混在里面？
