1. 审计范围

本页描述 H:\KeyenceAgent\kv-studio-operator 当前代码的整套运行方式。依据是 scripts/script_manifest.json、实际目录、flat executor、UI guard 和已产生的运行证据。

绿色：有直接证据黄色：已发布但真实回归不完整红色：明确失败或未验证

2. 总体架构

Agent 不拼接键盘、窗口或剪贴板动作。Workflow 只编排输入和步骤；Runner child 负责具体 UI 路线；所有进程级输入必须经过 Guard。

2.1 script_manifest.json：运行时授权表，不是说明文件

manifest 的根字段是 schema_version、layout_policy、customer_entry_policy、ui_atomic_actions、step_result_contracts 和 classes。它同时定义“谁可以被 Agent 调用”“内部脚本能被谁调用”“每步必须产生哪些结果文件”。

字段源码含义执行器如何使用
customer_entry_policy.allowed_classes允许客户态入口的类：customer_workflow、harness、scaffold tool、non-UI tool、gateresolver 拒绝 internal class 被直接当作 Agent API
classes.customer_workflowworkflow 路径、published/pending 状态、customer_callable、runner children、capabilities能力查询与 workflow 入口选择
classes.runner_child_approved允许被 workflow 调度的 UI 子脚本flat executor 仅接受 allowed classes
ui_atomic_actions.approvedGuard 中允许出现的全局输入函数名静态 gate 发现未分类 action 即失败
step_result_contracts每个脚本必须写的 JSON/artifact，支持 switch variantGet-KvStepContract 绑定本步骤验收文件

示例：runner_children/set_variables_guarded.ps1 默认必须写 set_variables_result.json 与 variable_persistence_validation.json；带 -SnapshotOnly 则必须写 variable_snapshot_result.json。

4.1 Flat Executor：执行计划的唯一 UI 调度器

源码：scripts/workflow_tools/invoke_kv_flat_execution_plan.ps1。它不是业务操作脚本；它是计划解释器和可靠性边界。Workflow 只写 plan，Executor 才依次启动 gate、workflow tool 或 runner child。

源码步骤具体行为工程意义
读取 plan要求 plan.ok=true、run_root、唯一 step.name、唯一 out_dir拒绝模糊或复用输出目录的执行
解析 manifest只允许 runner_child_approved、workflow_tool、gate 等类禁止 workflow 任意执行路径
取得 mutexWaitOne(0) 获取 Local\KeyenceAgent.KvStudio.UI不同 agent/process 不能并发操作同一桌面
指纹写 code_fingerprint.json、输入 SHA-256证据可追溯到当前代码与当前输入
Invoke-FlatWorkflowStep启动单步，写 step_started / step_succeeded / step_failed失败短路，禁止后续 UI 动作
最终验收按 contract 读取结果；需要编译时还校验当前 run 的 OK/NG 文本阻止旧文件或假阳性结果

5.4 设计审查要点

  • 发布状态不等于真实验证通过：必须查看同次 run.log、receipt 和语义结果。
  • 静态门禁只证明调用边界，不能证明焦点、粘贴、变量或程序体正确。
  • UIA 找到窗口不等于控件获得焦点；Guard 只保护前台，业务 runner 仍需证明表格状态。
  • 所有 workflow 必须 flat；客户 workflow 不应递归调用客户 workflow。
  • 每个新的全局输入动作必须先进入 Guard、manifest approved，再进入真实 workflow 回归。

7. 变量、FB 与数据类型工作流

对象原子路径输入验收

8. MNM 与程序体边界

MNM 是模块级导入/导出载体；程序体编辑列表是原位修改接口。两者不能混为同一验收：

MNM import
≠
程序体原位写入
≠
变量/FB 表格写入

程序体原位 workflow 的设计目标是 FB 和每次扫描执行型模块共用同一入口：定位模块、删除旧体、Ctrl+D、粘贴、Tab 一次、插入、关闭弹窗、保存。当前“设计目标”已实现为代码入口，但尚未完成 FB 与扫描模块两条正式真实回归。

10. 证据与结果契约

每次正式调用必须使用独立输出目录，至少包含：

计划execution_plan.json
code_fingerprint.json
日志run.log
workflow、锁、步骤、原子动作、错误和结果
步骤证据step_receipt.json
stdout/stderr
截图或快照
结果*_result.json
ok、error_code、输入、语义验收

Receipt hash 只证明证据属于本次运行，不替代变量、模块、程序体或编译结果的语义校验。失败后不能从旧运行目录寻找替代脚本或结果。

13. 源码摘录：Flat Executor

文件：scripts/workflow_tools/invoke_kv_flat_execution_plan.ps1。核心代码如下：

$plan = Get-Content -Raw -LiteralPath $PlanPath -Encoding UTF8 | ConvertFrom-Json
if ($plan.ok -isnot [bool] -or -not $plan.ok) { throw "Execution plan is not ok" }
$script:uiMutex = New-Object System.Threading.Mutex($false, 'Local\KeyenceAgent.KvStudio.UI')
if (-not $script:uiMutex.WaitOne(0)) {
  Write-WorkflowLog 'workflow_rejected' @{ error_code='KV_UI_WORKFLOW_BUSY' }
  throw 'KV_UI_WORKFLOW_BUSY'
}
foreach ($step in @($plan.steps)) {
  $path = Resolve-KvStudioOperatorScriptPath -ScriptRoot $scriptRoot `
    -Name ([string]$step.script_name) -Classes @($step.classes)
  Invoke-FlatWorkflowStep $step
}
Write-FlatWorkflowResult $plan $PlanPath $true 'pass' ''

这段代码说明：计划先验证，再加桌面互斥锁；每个 step 通过 resolver 解析，按数组顺序执行；失败在 Invoke-FlatWorkflowStep 处短路，最后聚合 workflow_result.json。

14. 源码摘录：UI Guard

文件：scripts/guards/kv_ui_guard.ps1。普通键盘动作的核心实现：

function Invoke-KvGuardedSendKeys {
  param([IntPtr]$TargetHwnd,[string]$Step,[string]$Keys,[string]$ExpectedTitleLike='')
  $watch = [Diagnostics.Stopwatch]::StartNew()
  $before = Assert-KvUiForegroundHwnd -ExpectedHwnd $TargetHwnd `
    -Step $Step -ExpectedTitleLike $ExpectedTitleLike -AllowSingleRecovery
  Write-KvUiGuardCheckpoint -Step $Step -Status 'before' -Before $before
  [System.Windows.Forms.SendKeys]::SendWait($Keys)
  $after = Assert-KvUiForegroundHwnd -ExpectedHwnd $TargetHwnd `
    -Step "$Step postcondition" -ExpectedTitleLike $ExpectedTitleLike -AllowSingleRecovery
  Write-KvUiGuardCheckpoint -Step $Step -Status 'after' -Before $before -After $after
  Complete-KvUiGuardAtomicAction -Stopwatch $watch -Step $Step `
    -Action 'SendKeys' -TargetHwnd $TargetHwnd
}

Guard 不负责判断 PLC 内容是否正确；它只保证输入前后目标窗口、前台状态、检查点和耗时边界。

18. 审阅顺序

scripts/script_manifest.json → workflows/*.ps1 → workflow_tools/invoke_kv_flat_execution_plan.ps1 → runner_children/*.ps1 → guards/kv_ui_guard.ps1 → 本次 run.log/result.json

这条顺序能区分 API 设计、调度安全、UI 输入实现和业务语义验收，避免把“脚本存在”或“静态门禁通过”误判为功能成功。
